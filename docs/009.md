# 1. 为什么收到 POST 数据以后还要验证

上一章已经可以：

```text
HTML 表单
↓
POST
↓
$_POST
↓
PHP
```

但用户可能提交：

```text
姓名：空
邮箱：abc
留言：空
```

PHP 能收到这些数据，并不代表这些数据有效。

因此需要增加：

```text
输入验证
```

---

# 2. 必填验证

最简单的验证：

```php
if ($name === '') {
    $errors['name'] = '请输入姓名。';
}
```

逻辑：

```text
姓名为空
↓
记录错误
↓
不继续当作有效数据使用
```

---

# 3. 邮箱验证

先检查是否为空：

```php
if ($email === '') {
    // 必填错误
}
```

再检查格式：

```php
filter_var(
    $email,
    FILTER_VALIDATE_EMAIL
)
```

例如：

```text
abc
```

不是有效邮箱。

而：

```text
hello@example.com
```

可以通过基础邮箱格式验证。

---

# 4. filter_input()

本实验使用：

```php
filter_input(
    INPUT_POST,
    'name',
    FILTER_UNSAFE_RAW
)
```

它表示：

```text
从 POST 输入中
↓
读取 name
```

这里使用：

```text
FILTER_UNSAFE_RAW
```

不是为了“自动保证安全”，而是明确读取原始输入。

后续仍然要：

```text
验证
+
安全输出
```

---

# 5. filter_var()

`filter_var()` 可以对一个已经获得的变量执行验证。

例如：

```php
filter_var(
    $email,
    FILTER_VALIDATE_EMAIL
)
```

如果邮箱格式不合法，会返回：

```php
false
```

---

# 6. 错误信息数组

本实验使用：

```php
$errors = [];
```

不同字段发生错误时：

```php
$errors['name'] = '请输入姓名。';
$errors['email'] = '请输入有效邮箱。';
```

这样可以形成：

```text
errors
│
├── name
├── email
└── message
```

HTML 页面可以分别显示对应错误。

---

# 7. 为什么不用一个 $error 字符串

如果只写：

```php
$error = '表单有错误';
```

就无法明确知道：

```text
哪个字段错了
为什么错
错误应该显示在哪里
```

使用：

```php
$errors['字段名']
```

更容易扩展。

---

# 8. 表单回填

验证失败后，不应该让用户重新输入所有内容。

因此：

```html
<input
    name="name"
    value="<?= e($name) ?>"
>
```

可以保留用户之前填写的数据。

这叫：

```text
表单回填
```

---

# 9. textarea 回填

`textarea` 不是使用 `value`：

```html
<textarea>
    内容
</textarea>
```

因此 PHP：

```php
<textarea><?= e($message) ?></textarea>
```

# 10. 输入验证和输出转义不是一回事

这是本章最重要的知识点之一。

## 输入验证

例如：

```text
邮箱是不是合法
姓名是不是为空
留言够不够长
```

属于：

```text
业务规则判断
```

---

## 输出转义

例如：

```php
htmlspecialchars()
```

属于：

```text
把文本安全地放进 HTML
```

因此不能认为：

```text
已经验证邮箱
=
不需要 htmlspecialchars()
```

两者解决的是不同问题。

---

# 11. htmlspecialchars()

本实验统一封装：

```php
function e(string $value): string
{
    return htmlspecialchars(
        $value,
        ENT_QUOTES,
        'UTF-8'
    );
}
```

以后输出：

```php
<?= e($name) ?>
```

而不是：

```php
<?= $name ?>
```

---

# 12. 为什么用户输入不能直接输出

假设用户输入 HTML：

```html
<strong>Hello</strong>
```

如果直接输出：

```php
<?= $name ?>
```

浏览器可能把它解析为 HTML。

使用：

```php
htmlspecialchars()
```

后，它会作为普通文本显示。

这是防止 XSS 的基础措施之一。

---

# 13. 服务器端验证非常重要

HTML 可以写：

```html
required
type="email"
```

浏览器会帮我们做基础验证。

但用户可以：

```text
关闭浏览器验证
手工构造请求
直接调用接口
```

因此真实 PHP 项目必须保留：

```text
服务器端验证
```

不能只依赖前端 HTML 或 JavaScript。

---

# 14. 本实验为什么暂时不保存数据

即使验证成功，本实验也只：

```text
显示提交结果
```

暂时不写：

```text
文件
数据库
邮件
```

因为本章只研究：

```text
接收
↓
验证
↓
输出
```

下一阶段再研究数据存储。

这样每个实验只解决一个主要问题。

# 15. 与数据库 CRUD 的关系

以后新增数据库记录：

```text
表单
↓
POST
↓
读取输入
↓
验证
↓
如果有错误
    返回表单
↓
如果没有错误
    PDO INSERT
```

因此：

```text
验证
```

必须发生在数据库写入之前。

---

# 16. 与 WordPress 的关系

WordPress 中常见：

```php
sanitize_text_field()
sanitize_email()
esc_html()
esc_attr()
```

这些函数虽然比本实验更具体，但背后的思想依然是：

```text
外部输入
↓
不要直接相信

页面输出
↓
不要直接输出
```

以后学习 WordPress 安全函数时会更容易理解。

## 3. 输入过短留言

例如：

```text

```

观察字符串长度验证。当前代码通过 `textLength()` 做兼容处理：

