# 实验 12：PHP Session 登录状态

本实验通过一个最小登录状态模拟，学习 PHP Session。

> 本实验只研究“状态管理”，不是真实账号系统，也没有密码验证。

---

## 实验目标

完成本实验后，应能够理解：

- `session_start()`
- `$_SESSION`
- `session_regenerate_id()`
- `session_destroy()`
- Session 登录状态判断
- 浏览器与服务器如何共同维持一个 Session
- Session 与 TXT / JSON 持久化数据的区别

# 1. Session 解决什么问题

HTTP 请求本身可以简单理解为：

```text
请求 1
结束

请求 2
结束

请求 3
结束
```

PHP 每次执行页面时，默认不会自动知道：

```text
这一次访问
和
上一次访问

是不是同一个用户
```

Session 就是用来帮助服务器维持：

```text
当前用户会话状态
```

---

# 2. session_start()

使用 Session 前必须先：

```php
session_start();
```

它的作用可以理解为：

```text
读取浏览器带来的 Session ID
↓
找到对应 Session 数据
↓
恢复 $_SESSION
```

如果是第一次访问，则会建立新的 Session。

---

# 3. session_start() 为什么要放在 HTML 输出之前

Session 通常依赖 HTTP Header 和 Cookie。

因此应该在：

```html
<!DOCTYPE html>
```

等页面内容输出之前调用：

```php
session_start();
```

否则可能出现：

```text
headers already sent
```

之类的问题。

---

# 4. $_SESSION

登录后，本实验保存：

```php
$_SESSION['username'] = $username;
```

还保存：

```php
$_SESSION['logged_in_at'] = date(...);
```

此时可以把：

```php
$_SESSION
```

理解为：

```php
[
    'username' => 'demo',
    'logged_in_at' => '...',
]
```

---

# 5. 判断是否登录

本实验使用：

```php
isset($_SESSION['username'])
```

如果存在：

```text
username
```

就认为当前处于模拟登录状态。

因此：

```text
Session 中有 username
↓
显示“已登录”

Session 中没有 username
↓
显示“未登录”
```

---

# 6. 为什么刷新页面后状态还存在

第一次登录：

```text
浏览器
↓
POST
↓
PHP
↓
写入 Session
```

随后刷新：

```text
浏览器再次访问
↓
带上 Session ID
↓
PHP 找到对应 Session
↓
恢复 $_SESSION
```

所以状态仍然存在。

---

# 7. Session 数据到底在哪里

可以先建立一个简化认识：

```text
浏览器
保存：
Session ID

服务器
保存：
Session 数据
```

例如：

```text
浏览器 Cookie
PHPSESSID = abc123
```

服务器根据：

```text
abc123
```

找到对应：

```text
username = demo
logged_in_at = ...
```

真实保存位置会受 PHP 的 Session 配置影响。

---

# 8. Session 与 Cookie 不一样

虽然 Session 常常依赖 Cookie 保存 Session ID，但：

```text
Session 数据
```

通常主要保存在服务器端。

浏览器通常只保存：

```text
Session ID
```

而 Cookie 可以直接保存某些数据在浏览器中。

下一章会专门研究 Cookie。

---

# 9. session_regenerate_id()

本实验登录成功后：

```php
session_regenerate_id(true);
```

它会生成新的 Session ID。

这是登录状态发生变化时常见的安全措施之一，可以降低 Session Fixation 风险。

当前阶段只需要记住：

> 登录成功等权限状态变化后，重新生成 Session ID 是一个良好习惯。

---

# 10. 退出登录

最简单的 Session 数据清空：

```php
$_SESSION = [];
```

然后：

```php
session_destroy();
```

本实验还同步删除 Session Cookie。

因此完整退出思路是：

```text
清空 $_SESSION
↓
删除 Session Cookie
↓
session_destroy()
```

---

# 11. Session 与 TXT / JSON 的区别

前两章保存：

```text
TXT
JSON
```

目标是：

```text
长期保存业务数据
```

例如：

```text
留言
产品
配置
记录
```

Session 更偏向：

```text
当前用户状态
```

例如：

```text
是否登录
当前用户 ID
购物车临时状态
一次性提示
当前流程步骤
```

---

# 12. 一个非常重要的区分

## TXT / JSON

关注：

```text
“系统有什么数据？”
```

例如：

```text
有哪些留言
有哪些产品
```

---

## Session

关注：

```text
“当前这个访问者处于什么状态？”
```

例如：

```text
当前是谁
是否登录
当前购物车是什么
```

---

# 13. Session 不应该代替数据库

真实登录系统通常是：

```text
数据库
保存：
用户账号
密码哈希
权限
资料
```

而：

```text
Session
保存：
当前已经登录的是哪个用户
```

所以真实流程更接近：

```text
用户提交账号密码
↓
数据库验证
↓
验证成功
↓
Session 保存 user_id
↓
后续请求根据 user_id 判断身份
```

---

# 14. 本实验为什么不做密码

如果现在加入：

```text
数据库
password_hash()
password_verify()
权限
CSRF
```

这一章就会变得过于复杂。

所以当前只研究：

```text
Session 如何保存状态
```

真实认证系统放到后期综合项目或进阶实验更合适。

---

# 15. 与 WordPress 的关系

WordPress 登录系统比这个实验复杂很多，但核心仍然需要解决：

```text
用户是谁
↓
是否已经登录
↓
具有什么权限
```

WordPress 会通过自己的认证 Cookie、用户系统和权限机制完成这些事情。

理解 PHP Session 后，会更容易理解：

> Web 应用为什么需要“会话状态”。

---

# 16. 与 WooCommerce 的关系

WooCommerce 也需要保存大量“当前访问者状态”，例如：

```text
购物车
临时结账信息
客户会话
```

具体实现不一定直接等于原生 PHP `$_SESSION`，但底层问题是相同的：

```text
不同 HTTP 请求之间
如何识别并保持当前用户状态
```

# 本章重点

最重要的是理解：

```text
PHP 变量
只存在一次请求

Session
可以跨多个请求保持“当前用户状态”
```

以及：

```text
业务数据
→ TXT / JSON / Database

当前会话状态
→ Session
```

不要把两类数据混在一起理解。
